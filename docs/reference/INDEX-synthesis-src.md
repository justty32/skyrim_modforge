# Synthesis source — navigation index

## What this is
A code-map of the Synthesis repo (Mutagen-Modding/Synthesis), a Mutagen-based patcher framework that runs user-written "patcher" executables over a Skyrim load order to produce a synthesized patch. Kept as read-only REFERENCE so we can find architecture/patterns for ModForge without re-exploring. All paths below are relative to `reference/`.

Key mental model: a Synthesis "patcher" is its own standalone .exe/.dll (built from a git or solution patcher). The pipeline does NOT call patchers in-process — it launches each one as a **subprocess**, passing CLI args, and even discovers a patcher's settings schema by running the patcher exe with a special query argument and reading JSON off stdout. The reflection→UI engine itself lives in the external `Mutagen.Bethesda.WPF` NuGet package; Synthesis only subclasses/configures it.

## Projects

### Mutagen.Bethesda.Synthesis — the library a patcher author references
The "SDK" linked into each patcher. Provides the `SynthesisPipeline` bootstrapper, the patcher `IPatcherState` (load order + link cache + patch mod), and the settings attribute/registration surface.
- `synthesis-src/Mutagen.Bethesda.Synthesis/Pipeline/SynthesisPipeline.cs` — central bootstrapper. `AddPatch<TMod,TModGetter>(...)` registers the patcher callback; `SetAutogeneratedSettings<TSetting>(nickname, path, out Lazy<TSetting>)` registers a reflection-driven settings class; dispatches CLI subcommands (`Run`, `OpenForSettings`, `SettingsQuery`, `CheckRunnability`). This is the single most important file.
- `synthesis-src/Mutagen.Bethesda.Synthesis/States/SynthesisState.cs` — concrete patcher state object handed to the patcher func: `LoadOrder`, `LinkCache`, `PatchMod`, `RawLoadOrder`, `AssetProvider`, settings-data paths, `Cancel` token.
- `synthesis-src/Mutagen.Bethesda.Synthesis/States/IPatcherState.cs` — the non-obsolete interface for the above.
- `synthesis-src/Mutagen.Bethesda.Synthesis/States/DI/PatcherStateFactory.cs` — builds the whole environment by hand (load order import, patch-mod create-or-import, link cache, asset/archive providers, FormKey allocator). The hand-rolled equivalent of a GameEnvironment.
- `synthesis-src/Mutagen.Bethesda.Synthesis/States/GetStateLoadOrder.cs` — assembles the final load order (implicit masters, Creation Club, inclusion/exclusion, trim-past-export-key, drop-disabled).
- `synthesis-src/Mutagen.Bethesda.Synthesis/Internal/ReflectionSettingsTarget.cs` — JSON (de)serialize of a settings class to/from a file next to the patcher; supplies defaults when absent.
- `synthesis-src/Mutagen.Bethesda.Synthesis/Settings/` — settings attributes patcher authors put on their settings classes: `SynthesisSettingName`, `SynthesisTooltip`, `SynthesisDescription`, `SynthesisOrder`, `SynthesisIgnoreSetting`, `SynthesisStaticEnumDictionary`, etc. (all thin subclasses of attributes from `Mutagen.Bethesda.WPF.Reflection.Attributes`).
- `synthesis-src/Mutagen.Bethesda.Synthesis/CLI/RunSynthesisMutagenPatcher.cs` — the run-arguments DTO (game release, data folder, load order path, output path, source path, localization, etc.) parsed from CLI.

### Synthesis.Bethesda — shared DTOs / protocol between pipeline and patcher
Small project of command DTOs and exit codes that define the host↔patcher CLI contract.
- `synthesis-src/Synthesis.Bethesda/Codes.cs` + `SettingsStyle.cs` — exit codes and settings-style enum used to signal "I autogenerate settings" vs "I open my own settings UI" vs "none".
- `synthesis-src/Synthesis.Bethesda/Commands/` — `RunSynthesisPatcher`, `OpenForSettings`, `SettingsQuery`, `CheckRunnability`, `IBaseRunArgs`, `HostSettings`: the verbs the patcher exe understands.
- `synthesis-src/Synthesis.Bethesda/DTO/ReflectionSettingsConfiguration.cs` + `PatcherListing.cs` — JSON shapes a patcher prints to advertise its settings/identity.

### Synthesis.Bethesda.Execution — the pipeline engine (no UI)
Everything for discovering, prepping, ordering, and running patchers as subprocesses, plus settings persistence and versioning. Heavily DI'd (Autofac modules under `Modules/`).
- `synthesis-src/Synthesis.Bethesda.Execution/Running/Runner/RunAPatcher.cs` — runs ONE patcher: builds args, creates output dir, invokes `prepBundle.Run.Run(args,...)` (a subprocess), finalizes/moves output, classifies failures.
- `synthesis-src/Synthesis.Bethesda.Execution/Running/Runner/RunAGroup.cs`, `RunAllGroups.cs`, `RunSomePatchers.cs` — the pipeline loop: groups → patchers, chaining each patcher's output as the next's source (`sourcePath`).
- `synthesis-src/Synthesis.Bethesda.Execution/Running/Runner/RunArgsConstructor.cs`, `LoadOrderForRunProvider.cs`, `MoveFinalResults.cs`, `FinalizePatcherRun.cs` — arg building, per-run load order, output plumbing.
- `synthesis-src/Synthesis.Bethesda.Execution/Patchers/Running/IPatcherRun.cs` and `Patchers/Cli/`, `Patchers/Git/`, `Patchers/Solution/` — patcher abstractions per source type (prebuilt CLI exe, git repo, local solution).
- `synthesis-src/Synthesis.Bethesda.Execution/PatcherCommands/GetSettingsStyle.cs` — KEY: discovers a patcher's settings by running its exe/project with a `SettingsQuery` arg and parsing the JSON/exit-code it prints (`LinesToReflectionConfigsParser.cs`).
- `synthesis-src/Synthesis.Bethesda.Execution/Settings/V2/` — current on-disk profile/pipeline schema: `PipelineSettings.cs`, `SynthesisProfile.cs`, `PatcherGroupSettings.cs`. `Settings/V1/` is the legacy schema + migration.
- `synthesis-src/Synthesis.Bethesda.Execution/Settings/Json/` — JSON parsing helpers incl. `LinesToReflectionConfigsParser.cs`.
- `synthesis-src/Synthesis.Bethesda.Execution/DotNet/` — locating/building/running the dotnet SDK to compile solution patchers on the fly.
- `synthesis-src/Synthesis.Bethesda.Execution/Modules/` — Autofac registration modules wiring the above.

### Synthesis.Bethesda.CLI — the command-line entry point
Thin CLI over the Execution engine using the `CommandLine` (CommandLineParser) library; each subcommand has a Module (Autofac) + Runner.
- `synthesis-src/Synthesis.Bethesda.CLI/Program.cs` — `Main`: `Parser.Default.ParseArguments(...).MapResult(...)` dispatching verb types to runners. Clean template for a multi-command CLI.
- `synthesis-src/Synthesis.Bethesda.CLI/RunPipeline/RunPipelineLogic.cs` — builds an Autofac container from `RunPipelineModule` and resolves/`Run()`s the pipeline. The pattern: command DTO → module → resolve logic → run.
- `synthesis-src/Synthesis.Bethesda.CLI/RunPipeline/` — full run pipeline wiring (`RunPatcherPipeline.cs`, `GetGroupRunners.cs`, `GetPatcherRunners.cs`, `ProfileLoadOrderProvider.cs`, `PipelineSettingsProvider.cs`).
- `synthesis-src/Synthesis.Bethesda.CLI/AddGitPatcher/`, `AddSolutionPatcher/`, `CreateProfileCli/`, `CreateTemplatePatcher/` — other verbs, each Module+Runner.
- `synthesis-src/Synthesis.Bethesda.CLI/CommonCliModule.cs` — shared CLI DI registrations.

### Mutagen.Bethesda.Synthesis.WPF — reusable WPF VMs/views for auto-generated settings
Reactive (ReactiveUI) view-models that turn a patcher's reflection settings config into editable UI. Wraps the engine in `Mutagen.Bethesda.WPF`.
- `synthesis-src/Mutagen.Bethesda.Synthesis.WPF/VMs/ReflectionSettingsVM.cs` — subclass of `Mutagen.Bethesda.WPF.Reflection.ReflectionSettingsVM`; THIS is where Synthesis hands a settings Type to the external reflection-UI engine.
- `synthesis-src/Mutagen.Bethesda.Synthesis.WPF/VMs/ProvideReflectionSettingsBundle.cs` — `ReflectionSettingsParameters.FromType(...)`: reflects over a settings class to produce a bundle of editable nodes.
- `synthesis-src/Mutagen.Bethesda.Synthesis.WPF/VMs/AutogeneratedSettingsVm.cs`, `ReflectionSettingsBundleVm.cs`, `ProvideAutogeneratedSettings.cs` — orchestration + load-order/link-cache feeding into the settings UI (so FormKey pickers know the load order).
- `synthesis-src/Mutagen.Bethesda.Synthesis.WPF/Views/AutogeneratedSettingsView.xaml.cs` — the host view.

### Synthesis.Bethesda.SettingsHost — standalone settings-editor window
A tiny WPF app a patcher launches to edit its own autogenerated settings outside the main GUI (when "OpenForSettings").
- `synthesis-src/Synthesis.Bethesda.SettingsHost/MainVM.cs` — gets the live load order, calls `GetSettingsStyle` against the patcher, and hosts an `AutogeneratedSettingsVM`; `Save()` writes JSON back.
- `synthesis-src/Synthesis.Bethesda.SettingsHost/MainWindow.xaml.cs`, `App.xaml.cs`.

### Synthesis.Bethesda.GUI — the full WPF application

## Patterns worth stealing for ModForge

### (a) Auto-generated settings: a plain C# class becomes both JSON config and edit-UI
The whole flow, end to end:
1. Patcher author declares a POCO settings class, decorates fields with attributes (`synthesis-src/Mutagen.Bethesda.Synthesis/Settings/SynthesisSettingName.cs`, `SynthesisTooltip.cs`, `SynthesisOrder.cs`, `SynthesisIgnoreSetting.cs`, …) and registers it via `SetAutogeneratedSettings<TSetting>(...)` in `SynthesisPipeline.cs:223`.
2. Persistence is dumb JSON round-trip in `ReflectionSettingsTarget.cs` — read `{settingsPath}` next to the patcher, deserialize to `TSetting`, or hand back `new TSetting()` defaults. `ObjectCreationHandling.Replace` + Mutagen JSON converters (FormKeys) make it work for Bethesda types.
3. Schema discovery is process-based: the host runs the patcher with a `SettingsQuery` verb; the patcher prints `ReflectionSettingsConfigs` JSON and returns a `Codes.AutogeneratedSettingsClass` exit code (`SynthesisPipeline.cs:275` `QuerySettings`). Host side: `synthesis-src/Synthesis.Bethesda.Execution/PatcherCommands/GetSettingsStyle.cs`.
4. UI is generated by reflecting over the Type: `ProvideReflectionSettingsBundle.cs` → `ReflectionSettingsParameters.FromType(...)` → `ReflectionSettingsVM` (the actual reflection→control mapping lives in the external `Mutagen.Bethesda.WPF.Reflection` package). The load order + link cache are injected so FormKey/FormList fields render as record pickers.
For ModForge (JSON-spec driven), the reusable idea is steps 1–2: decorate a spec/settings class with metadata attributes and get JSON (de)serialize + defaults for free, and the attribute-driven metadata model from `Mutagen.Bethesda.WPF.Reflection.Attributes`.

### (b) Constructing the Mutagen environment / load order
Synthesis does NOT use `GameEnvironment.Typical`; it builds the pieces explicitly in `synthesis-src/Mutagen.Bethesda.Synthesis/States/DI/PatcherStateFactory.cs`: order the listings (`GetStateLoadOrder.cs`), import the load order via `LoadOrderImporterFactory`, create-or-import the patch mod with `ModFactory<T>.Activator/Importer` (header-version + FormID-range overrides, localization, optional `TextFileSharedFormKeyAllocator`), then build an immutable/mutable `LinkCache` and a hand-assembled `GameAssetProvider`/archive stack. This is the closest analog to what ModForge needs when it creates a NEW plugin: see `ModFactory<TModSetter>.Activator(exportKey, gameRelease, headerVersion, forceUseLowerFormIDRanges)` at `PatcherStateFactory.cs:232`.

### (c) CLI structure
`synthesis-src/Synthesis.Bethesda.CLI/Program.cs` is a compact, copyable template: `CommandLineParser` (`Parser.Default.ParseArguments(args, typeof(VerbA), typeof(VerbB), …).MapResult(async (VerbA c)=>…, …)`). Each verb is a `[Verb]`-attributed DTO (e.g. `synthesis-src/Synthesis.Bethesda/Commands/`), and each runner builds its own Autofac container from a per-command Module then resolves a logic class (`RunPipelineLogic.cs` is the canonical example). Clean separation: parse → DTO → module → resolve → run.

### (d) Invoking a patcher and pipelining many
Patchers are run as **subprocesses chained by file**: `synthesis-src/Synthesis.Bethesda.Execution/Running/Runner/RunAllGroups.cs` → `RunAGroup.cs` → `RunSomePatchers.cs` → `RunAPatcher.cs`. Each `RunAPatcher.Run(...)` constructs CLI args (`RunArgsConstructor.cs`), runs the patcher, and the framework feeds one patcher's output mod as the next patcher's `sourcePath` (so it's an incremental pipeline over a single synthesized patch). Output finalization/moving is in `MoveFinalResults.cs` / `FinalizePatcherRun.cs`. The patcher-type abstraction (`IPatcherRun` + `Patchers/{Cli,Git,Solution}/`) lets the same loop run prebuilt exes, cloned git repos, or locally compiled solutions.
