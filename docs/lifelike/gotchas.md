# Gotchas — the traps that bit us, with the fix

Grouped by area. Each row is symptom → root cause → fix. These are the failure modes that
cost real debugging time; the fix column is the proven workaround.

← back to [lifelike hub](README.md) · see also [engine-internals](../engine-internals.md) for the "why"

## NPC behaviour (packages, combat, speech)

| Symptom | Root cause | Fix |
|---|---|---|
| Generated package's `target` reads as `LocationTarget` instead of `LocationFallback` even though we used `new LocationFallback()` | Mutagen picks the binary shape from `LocationFallback.Type` enum, NOT the C# class | `new LocationFallback { Type = LocationTargetRadius.LocationType.NearSelf }` |
| Sandbox-equipped NPC stands still indefinitely doing nothing | Used `Type = NearEditorLocation` — needs CK-set Editor Location which Mutagen-generated NPCs lack | Use `Type = NearSelf` — anchors at current position, no external link |
| NPC doesn't move, just stands at spawn (after ~1 min delay still nothing) | Sandbox finds no furniture / idle markers / other NPCs nearby — barren area | Move spawn to a populated cell (Bannered Mare, Sleeping Giant Inn). Sandbox **needs** content to interact with |
| Sandbox NPC stands still for the first 30–90 seconds after cell load | Engine sandbox cold-start delay; normal | **Wait the full minute** before declaring failure — vanilla NPCs hide this because they're initialised long before the player arrives |
| Travel package in spec but NPC ignores it (sandboxes locally instead) | Engine silently rejected cross-cell Travel — NPC has no "citizen" identity to traverse city gates | Set `crimeFaction` + add the town's faction to `factions` + `unique: true` |
| NPC walks but never speaks; only mumbles "嗯/啊" when approached | No voiceType set, OR voice set but no faction-conditioned dialogue topics match | Set `voiceType: MaleNord` (or similar). For more chatter, add a town faction so faction-conditioned dialogue topics apply |
| Mage NPC just runs away from any threat | `Aggression=Unaggressive + Confidence=Cowardly` (Mutagen defaults) — flees regardless of CombatStyle | `aggression: "Aggressive"` + `confidence: "Brave"` |
| Townsperson treats the player as hostile / starts fights | `aggression: "Aggressive"` makes an NPC *initiate* | For a defend-but-don't-initiate NPC use `aggression: "Unaggressive"` + `confidence: "Brave"` — aggression governs initiation, Brave governs flee-vs-stand once attacked |
| UseMagic NPC stands at location but NEVER casts | Slot 3 "Spell" authored as `PackageTargetObjectType` (category enum). All 46 vanilla UseMagic packages use `PackageTargetObjectID` with a FormLink to a specific SPEL | Spec field `useMagic.spell: "<master>:0xFORMID"` of the SPEL; Build writes `PackageTargetObjectID` |
| UseMagic NPC casts 1-2 times then stops forever | `numToCastMax` is **total package-lifetime casts**, not per-cycle. With `schedule.durationInMinutes=0` the package completes the moment its quota's hit | `numToCastMax: 1000` + `schedule.durationInMinutes: 1440` (24h continuous), mirroring vanilla `WCollegeOnmundPracticeFlames12x4` |
| UseMagic NPC stops casting when combat starts | Combat AI preempts idle packages (vanilla behaviour) | Add `flags: [ "IgnoreCombat" ]` like vanilla `SprigganCallOverride` if casting must continue (e.g. boss ritual) |
| A scheduled package (Sleep at night, a meal-time Sandbox) never runs, or the wrong one runs at the wrong hour | The NPC's `packages` list is evaluated in **order = priority**: the engine runs the **first** package whose schedule window **and** conditions currently pass. An unconditioned package (`schedule.hour = -1` ⇒ "any time") placed **above** a scheduled one wins at every hour, so the scheduled package below it is never reached | Order **specific → general**: scheduled/conditioned packages FIRST, the unconditioned fallback LAST. A schedule window is `[hour, hour + durationInMinutes)`; `hour = -1` = no time gate. E.g. `[ "MF_NightSleep" (h=22 dur=540), "MF_Sandbox" (unconditioned) ]` — sleep 22:00–07:00, sandbox the rest |
| Sleep package (template `0x019717`) NPC locks the inn / shared building she sleeps in | `sleep.lockDoors` defaults **true** (vanilla behaviour: an NPC locks its *own house* at night) | Set `sleep.lockDoors: false` for any follower/NPC bedding down in a shared or public space (an inn, a barracks) |
| Generated combat spell never gets cast (NPC melees instead) | The SPEL has no `equipType` — an NPC can't equip an un-equippable spell to a hand | Set `spells[].equipType: "Skyrim.esm:0x013F44"` (EitherHand) |
| Patrol NPC (or any path-to-marker behaviour) stands still, never moves | A **static REFR does NOT snap to the floor** like an actor does — a marker at a guessed exterior z lands off-navmesh, so pathing silently fails | Anchor markers on coords PROVEN walkable: `refpos <plugin> <0xFORMID>` to copy a vanilla reachable ref's position, or place inside a hand-navmeshed interior. Actors (ACHR) snap to ground; markers (REFR) do not |
| **CRASH at main menu / load** when a plugin contains a programmatically-built **NAVM + NAVI** (the abandoned `autoNavmesh`) — **ROOT-CAUSED 2026-06-01 from a CrashLoggerSSE log** | Access-violation in `InitTESThread` → Engine Fixes `PrecomputedPaths::NavMeshInfoMap_InitItemImpl` walking our NAVI `[0x0A000804]`: it reads each `NavMeshInfo`'s **`pathingCell`** pointer (`mov edx,[rcx+0x10]`, rcx=0 → null deref). A non-CK navmesh has **no PathingCell / preferred-path graph** — that structure is generated by the CK's **"Finalize Navmesh"** pass, NOT stored as authorable plugin bytes. A half-built NAVI is **worse than none**: a cell with no navmesh still loads (NPCs just stand/sandbox, can't path — see doors/vendor examples); a cell with an un-finalized NAVI **CTDs at load** | **Never emit NAVM/NAVI from a generator.** `autoNavmesh` is a confirmed dead end and was never merged to master. A new cell that needs real pathing must be navmeshed + **Finalize Navmesh**'d in the Creation Kit. If you only need an NPC to stand/idle, ship the cell with NO navmesh + a Sandbox package |
| Want a hireable follower but the "Follow me" topic never appears (IN-GAME CONFIRMED It.24, 2026-05-30) | The vanilla free-follow hire topic (`DialogueFavorGenericFollowBranchTopic`) is gated on a STACK of conditions, found by probing it: `GetIsVoiceType` ∈ **VoicesFollowerNeutral (`0x0D23AC`)**, `GetInFaction PotentialFollowerFaction (0x05C84D)==1`, `GetRelationshipRank player >= 1`, `GetInFaction CurrentFollowerFaction(0x05C84E)==0`, `GetInFaction PotentialHireling(0x0BCC9A)==0`, player follower-count global==0. Plus the NPC must be **conversable** (have a Hello — custom NPCs aren't talkable from the follower topics alone). The two that bit us: **(a) the voice was FemaleNord/MaleNord — CITIZEN voices NOT in the follower list**, so GetIsVoiceType failed (this was the last blocker; once fixed, `setrelationshiprank player 3` made hire work in-game); **(b) a static `relationships[]` RELA to the player reads rank 0 at runtime — it DOES NOT WORK. Vanilla has 642 RELA records and ZERO reference the player (0x14): player relationships are ALWAYS set at runtime by script (`SetRelationshipRank`), never a static RELA.** So a free-follow custom follower needs either a Papyrus script (`seraRef.SetRelationshipRank(Game.GetPlayer(), 3)`) OR the **paid-hireling** path (add `PotentialHireling 0x0BCC9A` to `factions` — that hire topic is gated on faction membership, not relationship, so it works from static records). **IMPLEMENTED (It.26):** the example `examples/follower_hireable_spec.json` now lists `Skyrim.esm:0x0BCC9A` in `factions` as the primary recruit path — no generator change was needed since faction refs already resolve generically as `<master>:0xFORMID` and are added at rank 0 (the vanilla-mercenary convention); the script-only free-follow path is no longer required to get an in-game-recruitable follower. **⚠ REFUTED It.27 (2026-05-31), see next row — PotentialHireling membership alone does NOT recruit a custom NPC.** | Use a **follower voice**: female `FemaleEvenToned 0x013ADD` / `FemaleSultry 0x013AE0` / `FemaleCondescending 0x013AE4` / `FemaleYoungEager 0x013ADC`; male `MaleEvenToned 0x013AD2` / `MaleYoungEager 0x013AD1` / `MaleEvenTonedAccented 0x0EA267`. Add `0x05C84D` to `factions`, a `relationships[]` Ally to `0x000014`, and set `greeting` (Build emits the host quest + Hello so she's conversable). If the RELA still reads 0 in-game, `setrelationshiprank player 3` on her confirms the rest works |
| Paid-hireling recruit topic appears at gold<500 but VANISHES at gold≥500 (IN-GAME It.26, root-caused It.27 via the new `infodiag`) | `HirelingQuestTopic1` (`0x0BCC84`) serves the **first** INFO whose CTDA stack passes. Probed with `infodiag Skyrim.esm 0x0BCC84`: INFO[0] (the "come back with coin" **refusal**) needs only `CurrentHireling(0x0BD738)==0 & PotentialHireling(0x0BCC9A)==1 & GetItemCount Gold < threshold` → passes for any PotentialHireling member while poor. But every **recruit** INFO (gold ≥ global `0x0F11B5`, runs the take-500-gold + add-to-CurrentHireling result script) ALSO carries `GetIsID == <a specific vanilla HirelingX>` — HirelingMarcurio `0x0B9980`, HirelingVorstag `0x0B997F`, HirelingErikTheSlayer `0x065657`, … There is **no generic faction-only recruit INFO**; vanilla hardcodes one per mercenary. So a custom NPC: poor → refusal INFO passes (topic shows); rich → refusal fails (gold not <threshold) AND every recruit INFO fails `GetIsID(≠custom)` → **topic dropped entirely**. The It.26 hypothesis (GetRelationshipRank reading 0) was WRONG — the discriminator is **GetIsID**, not relationship. **Conclusion: the paid path canNOT recruit an arbitrary custom NPC from static records; a script is unavoidable either way.** | Don't rely on PotentialHireling alone for recruit. Two working fixes, both shipped: **(a) DONE It.27 (in-game confirmed)** — free-follow + a Papyrus start-fragment `SetRelationshipRank(player,3)` (that topic gates on relationship+follower-voice, NOT GetIsID; `examples/follower_hireable_spec.json`). **(b) DONE It.28** — our OWN paid recruit topic with an OnEnd result fragment (RemoveItem Gold001×500 + `AddToFaction CurrentFollowerFaction 0x05C84E` + `SetPlayerTeammate(true)`; `examples/follower_paid_spec.json` + `MFHirePaidRecruit.psc`). KEY: joining the follower system = CurrentFollowerFaction + SetPlayerTeammate; the GENERIC vanilla follow/wait/dismiss dialogue (dismiss INFO[17] of `0x05C80C`) gates only on that faction + follower voice + PotentialHireling==0 — NO GetIsID — so it works for a custom NPC with no DialogueFollower-quest integration. Always probe first: `infodiag <esp> <topicFormId> [substr]` dumps any topic's full CTDA stack (and now its OnEnd VMAD fragment). **UPDATE It.30/It.32:** adding her to `CurrentFollowerFaction` makes the GENERIC vanilla *dismiss* line appear but it CANNOT release her (that line is driven by the DialogueFollower quest, which only dismisses followers it `ForceRefTo`'d into its alias) — so (b) had to ALSO author its own dismiss (self-managed). **The cleaner, now-PREFERRED paid path is (c):** call `DialogueFollowerScript.SetFollower(akSpeaker)` from the recruit fragment (`examples/follower_vanilla_spec.json`) — vanilla then manages trade/wait/dismiss and AFT/EFF/NFF integrate; gate the line on `GetGlobalValue PlayerFollowerCount(0x0BCC98)==0`. Custom CombatStyle + dialogue survive follower status; sandbox packages only yield while actively following |
| **CRASH at main menu** when a mod with a `relationships[]` entry is enabled | RELA `parent`/`child` must point at an **NPC_ base record**; the player's is `Skyrim.esm:0x000014`. `0x000007` is **PlayerRef** (the placed ACHR) — a RELA pointing at an ACHR is a type mismatch the engine rejects at load | Use `child: "Skyrim.esm:0x000014"`. (Was the wrong default in `RelationshipSpec.Child` — found via byte-compare to a working mod, fixed.) |
| **CRASH at main menu** when a mod with custom `dialogue[]` is enabled | Generated `DialogTopic` left **SNAM (subtype name) = null** (`0x00000000`). Every vanilla `Custom` topic carries SNAM=`'CUST'`; an empty subtype crashes the engine while it builds the dialogue-topic index at load | Set `topic.SubtypeName = new RecordType("CUST")` alongside `Subtype = Custom`. Fixed in `Generator.Build.cs`; when composing topics by hand via the library, set both. Confirm with a vanilla probe: every Custom DIAL has SNAM=`'CUST'` |
| Custom dialogue doesn't crash but **the topic never appears** (IN-GAME CONFIRMED fix It.23, 2026-05-30) | A stack of missing pieces, found by raw-subrecord diff against a working vanilla topic (MS11). The **decisive** one: each player **INFO was missing `ENAM` (info flags) + `CNAM` (favor level)** — Mutagen omits them when `Flags`/`FavorLevel` are unset, and an INFO with no `ENAM` is treated as **invalid**, so a topic whose only INFO is invalid is silently dropped from the menu. Also required: a **DialogView (DLVW)** per quest (ties branches to the quest) and a **Hello** info (makes the NPC conversable at all) | On every generated INFO set `Flags = new DialogResponseFlags()` (→ENAM) and `FavorLevel = FavorLevel.None` (→CNAM). Plus emit one **DLVW** per quest (`Quest` + player `Branches` + `ENAM`=4×0/`DNAM`=[1]) and a **Hello** per speaker (`Misc`/`Hello`/`SNAM='HELO'`, no branch, `GetIsID(speaker)`). All in `Generator.Build.cs`. Verify with a raw subrecord diff: a working vanilla player INFO is `ENAM CNAM TRDT NAM1 NAM2 NAM3 … CTDA` |
| Multiple custom topics, ONE works in isolation but with 2+ the NPC goes mute again (IN-GAME It.25) | All player topics shared the **same `Priority` (50)**. Vanilla never has two simultaneously-valid top-level topics share a priority. **Caveat:** this fix coincided with a fresh-new-game test, so it may be confounded with the save/load issue below — kept anyway as good practice (it matches vanilla and can't hurt) | Give each topic a **distinct priority**. Build hands out a descending sequence (90, 89, 88, …). |
| **Custom dialogue NEVER appears unless the game was LOADED after the quest started** — `coc`-from-main-menu or mid-session `startquest` leaves the NPC mute even with a perfect plugin + running quest (THE root cause of the whole It.23–26 dialogue saga; IN-GAME CONFIRMED 2026-05-30) | Skyrim registers a quest's player dialogue **at game-load time**, not when the quest starts. A brand-new game runs that load step (so dialogue works); but loading into the world via `coc` from the main menu, or `startquest`-ing mid-session, never re-registers the dialogue → the topic/Hello silently never attaches to the NPC. This masqueraded as a dozen different "structural" bugs because the plugin was fine all along | **Testing:** after the quest is running, **`save` then `load`** that save (forces dialogue re-registration) — or just start a genuine new game and let it finish initializing before `coc`. **Never** trust a main-menu-`coc` or a mid-session `startquest` to surface dialogue. This is a save/runtime rule. **For real users on existing saves the fix is a `.seq` file — see next row.** |
| **On an EXISTING save (made before the plugin), a Start-Game-Enabled dialogue quest does NOT auto-start on first load** → its dialogue is missing until a `save`+`reload`. New games are fine; this is why third-party followers (Sofia) "just work" but ModForge dialogue needed a save/reload (IN-GAME CONFIRMED fix 2026-05-31: with the `.seq`, follower_vanilla talks on an old save with no save/reload) | The engine only force-starts SGE quests on save-load if they're listed in a **`.seq` (sequence) file** at `Data/Seq/<plugin>.seq` — a flat array of 4-byte LE quest FormIDs. ModForge generated the `.esp` but no `.seq`, so the SGE quest stayed un-started on existing-save load (a NEW game starts all SGE quests during init regardless, masking the gap) | **`build`/`package` now auto-write `Seq/<plugin>.seq`** for every SGE quest (incl. the auto `_GreetQuest`s) — see `SeqFile.cs`. Ship the `Seq/` folder alongside the plugin. Load-order independent (engine resolves the FormIDs against the file's plugin by filename); if a corner case breaks, regenerate with xEdit's *Create SEQ File* under the live load order |
| A no-package NPC placed at cell origin **(0,0,0)** can't be reached/talked to — you end up activating a nearby vanilla NPC instead | (0,0,0) is the cell ORIGIN, usually inside a wall / off-navmesh in a corner. It.16-22 NPCs "worked" from (0,0,0) only because their Travel/Sandbox packages walked them onto navmesh immediately; a standing (no-package) NPC just stays stuck there | Place at a real in-room coordinate near the vanilla NPCs (find theirs by dumping the cell's ACHRs). Actors snap to navmesh, so any sane in-room point works — e.g. Sleeping Giant Inn common room ≈ (-350,180,0) |
| Custom dialogue response subtitle flashes by / is unreadable (or the NPC seems mute) | Unvoiced lines get ~0 duration from the (missing) voice file — Skyrim zooms past them | Install **[Fuz Ro D-oh — Silent Voice](https://www.nexusmods.com/skyrimspecialedition/mods/15109)** (calculates duration from text length for all unvoiced lines) **or** bundle a silent `.fuz` per line at `Sound/Voice/<plugin>/<voicetype>/<info>_<formid>.fuz`. Also turn on dialogue subtitles |

## Cells, worldspace, lighting

| Symptom | Root cause | Fix |
|---|---|---|
| Headless build throws "Could not determine plugin listings path" while cloning a vanilla record | Copying a localized `TranslatedString` (Name/Description/BookText) triggers an all-string-source resolve that needs plugins.txt/load-order — absent headless on Linux | Pass a `TranslationMask { Name=false, … }` to `DeepCopyIn` (you override those anyway). Same landmine hits `GetOrAddAsOverride` on cells and `find`'s Name resolution |
| Whole world floods / "everything underwater" after an exterior placement | An override Cell/Worldspace does NOT inherit omitted data from the master — the engine defaults them. Dropping `LandDefaults` reset `DefaultWaterHeight` from Tamriel's real -14000 to 0 | Hand-copy env subrecords (`CopyWorldspaceEnv` / `CopyCellEnv`), skipping only the localized Name + the giant child structures. (A cell's own `WaterHeight=FLT_MAX` is just a "use worldspace default" sentinel — a red herring) |
| Save / HUD shows "unknown location" after a worldspace override | Minimal override blanked the localized worldspace Name (unreadable headless) | Restate a plain Name (`"Skyrim"` for Tamriel `0x3C`); other worldspaces need a future spec field |
| Vanilla interior-cell override silently IGNORED (placed objects don't appear, lighting unchanged) | Interior cells are grouped into block/sub-block GRUPs **by FormID**; an override in the wrong GRUP is never matched to the master | Compute the GRUP from the cell FormID: **block = id % 10, sub = (id/10) % 10** (decimal, 24-bit ID). See [engine-internals](../engine-internals.md#interior-cell-grup-formula) |
| New in-spec interior cell renders pitch-black / player falls into the void on `coc` | A brand-new cell has no Lighting/LightingTemplate and no floor geometry | Give `cells[].template` a vanilla interior ref (for lighting via `CopyCellEnv`); add a placed-static floor grid (e.g. `WRIntFloorSTMid01Large 0x1044AA`) |
| An NPC placed in a new cell with **no floor** behaves wrong downstream — e.g. a merchant whose trade menu never opens (IN-GAME CONFIRMED 2026-05-31) | The NPC drops into the void in a **perpetual falling state**, so it never settles into its idle/sandbox "on-duty" state — and condition functions that gate on being settled (e.g. `GetOffersServicesNow` for a vendor) stay 0. The records can be perfect; the NPC just never reaches the state that satisfies them | Always lay a **floor** under any placed NPC in a new cell (`WRIntFloorSTMid01Large 0x1044AA` grid) **and** give it an on-duty package (a `Sandbox 0x01C254` NearSelf for a counter NPC) so it stands in place. Confirmed for the merchant: with floor + sandbox + `VendorLocation`=cell, the barter menu opens |
| Placed light illuminates almost nothing (room feels unlit/flat) | The light base is `PortalStrict` (e.g. `DefaultSunlightHalfOmni01 0x0172C4`) — only lights inside a room portal, and an open cell has no room markers | Use a non-PortalStrict omni shadow light (`WRShadowOmni 0x0C82AE`, radius 512) as the key + non-shadow fills (`WRInteriorLightBrite01 0x06ED46`) |
| `coc`-spawned player lands slightly inside/under the floor | `coc` with no COC marker spawns at cell origin (0,0,0); a floor mesh whose pivot isn't at its top surface puts you in it | `tcl` to check; nudge floor z or add a COC marker. Match floor-tile spacing to the real mesh size or gaps show |
| `coc <interior>` then walk out → terrain LOD breaks at the city gate | `coc` skips the normal load screen, exterior LOD doesn't preload | Fast-travel away + back, OR `coc <exteriorMarker>` directly |

## Items, models, magic effects

| Symptom | Root cause | Fix |
|---|---|---|
| Generated item appears with no model when dropped (or crashes on equip/read) | Weapon/Book/Misc/Potion has no `.nif` — fine in inventory, but CRASHES on any scene interaction (weapon equip, book 3D-read) | Set `template: "<master>:0xFORMID"` to clone a vanilla record's model (IronSword `0x012EB7`, Book1CheapNordsArise `0x0ED161`, GemRuby `0x063B42`, RestoreHealth06 `0x039BE5`) |
| Generated **armor equips INVISIBLE** (character looks naked, but the ARMO is in inventory with correct stats/enchant) — **FIXED + IN-GAME CONFIRMED 2026-06-01** (templated cuirass shows the iron-armor mesh when worn) | The worn mesh of an ARMO lives on its **Armature** (ARMA addon records), *not* on the ARMO itself. A spec armor with only a `BodyTemplate` (armorType + slots) has an **empty Armature** → nothing renders when equipped. Unlike weapons this does NOT crash — it silently shows nothing | Set `template: "<master>:0xFORMID"` to clone a vanilla armor of the same slot (ArmorIronCuirass `0x00012E49`); `DeepCopyIn` brings its Armature (worn mesh per body part) + WorldModel (ground model) + BodyTemplate. Build now **warns** when an armor has no `template`. Optional `model` overrides only the ground/world `.nif`; the worn mesh still comes from the template's Armature, so pair `model` with a `template` |
| Player **learns a custom shout but can't shout it** — the word fires no spell, nothing happens (IN-GAME 2026-06-01: shout learned via AddShout, but the Thu'um does nothing) | Each shout word points at a **Voice-type SPEL**, and a SPEL with **no `EquipmentType` (EQUP)** has no equip slot — the engine can't equip it to the voice, so pressing Shout does nothing. ModForge only set EQUP when the spec gave one explicitly; Voice spells (built without one) came out slot-less. Vanilla shout word-spells ALL carry **EitherHand (`Skyrim.esm:0x00013F44`)** — same EQUP as hand spells | Build now **defaults castable spell types (Spell/Voice/Power/LesserPower) to EitherHand** when `equipType` is omitted. Set `equipType` only to override. (Also give the SHOU a `menuDisplayObject` like `Skyrim.esm:0x0A59AC` so it previews in the shout menu.) |
| Custom shout fires its projectile/effect but makes **no Thu'um voice** (no "FUS RO DAH" yell) | The shouted voice is the MGEF's **Release sound** (a `VOCShoutFX…` SoundDescriptor) — not the projectile's. A shout MGEF with no `sounds` casts silently | Give the MGEF `sounds: [{ type: "Release", sound: "<master>:0xFORMID" }]`. Vanilla voices: Unrelenting Force `0x0A0F52/53/54` (A/B/C charge levels), Frost Breath `0x07F8E6/07F8E7`, Fire Breath C `0x072915`. For a 3-level yell, use 3 MGEFs (one per word-spell) each with its own A/B/C Release sound |
| Cloned potion gives a doubled/stacked effect | `DeepCopyIn` keeps the template's own effects, which then stack with the spec's effects | Build does `r.Effects.Clear()` after the clone before wiring spec effects — just don't re-add the template's effect in your spec |
| Custom MGEF heal spell casts but doesn't heal | `Recover` flag on an instant effect reverts the heal the instant the effect "ends" (immediately) | Instant effects (duration 0) must use `["NoDuration","NoArea"]` and NO `Recover`. `Recover` is correct only for a **timed** fortify (e.g. +50 Health/60s) |
| Custom effect costs absurd magicka | High `baseCost` × magnitude under autocalc | Keep `baseCost` low; the autocalc formula multiplies it by magnitude |
| **CRASH while "Loading Files"** when a mod with an **entry-point perk** is enabled (surfaces as "two mods crash together" — it's memory-layout-sensitive, so one plugin alone may load by luck; IN-GAME root-caused 2026-05-31 from a CrashLoggerSSE log naming the `BGSEntryPointPerkEntry`) | An entry-point perk effect (`PerkEntryPointModifyValue`) was written with `PerkConditionTabCount = 0`. That byte is the entry point's **intrinsic condition-tab count** (attacker/target/weapon contexts), not the number of conditions you author; the engine sizes a per-tab array from it, so a `PRKC` tab on index 0 with count 0 **overflows the array → garbage FormID lookup → access-violation CTD**. Mutagen ignores the byte on read (uses the real `Conditions` list), so dump/round-trip/link-resolution/ESL-header all pass — only the runtime parser crashes | `Build` sets `PerkConditionTabCount` from a vanilla table (`ModAttackDamage`/`ModSpellMagnitude` = 3, `ModArmorRating` = 2, `ModSkillUse` = 1, … unlisted → 2; never 0). Regenerate by scanning Skyrim.esm's PERK records grouping `EntryPoint → PerkConditionTabCount`. See [engine-internals](../engine-internals.md#perk-entry-points-carry-a-hidden-tab-count-byte) |

## Dialogue

| Symptom | Root cause | Fix |
|---|---|---|
| Custom dialogue records are valid but the topic NEVER appears when you talk to the NPC | Two flags missing: the host **Quest isn't Start Game Enabled** (so it never runs → its dialogue never loads) and/or the **DialogBranch isn't Top-Level** (so the topic is a sub-branch, not a menu option) | Quest `flags |= StartGameEnabled` (+ a `Priority`); branch `Flags = TopLevel`. In ModForge: `quests[].startGameEnabled` (default true) + automatic on the dialogue branch |
| Menu line is mislabelled / wrong text shows | INFO `Prompt` was set, overriding the menu line | Leave INFO `ResponseData` null (uses your own Responses) and `Prompt` null — the menu line comes from `topic.Name` |
| Custom dialogue line shows no audio / NPC lips don't move | No recorded voice (.fuz/.lip) — expected for generated dialogue | Turn **General + Dialogue Subtitles ON** (Settings ▸ Display) — the line still shows as a subtitle and the menu option still works; that's a valid in-game confirmation |
