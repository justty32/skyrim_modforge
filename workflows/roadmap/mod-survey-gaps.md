## ⚠️ 降級為 partial（大部分已支援，只剩窄缺口）

- **SM branch/quest-node 子樹 + keyword 路由** — `Generator.Build.StoryManager.cs:BuildStoryManager()` 已建 SMBN+SMQN、以 `PreviousSibling` 串同層 quest node、按 `root|keyword` 一分支路由（帶 `GetEventData/GetIsID Keyword` 條件）。**真缺**:只建 vanilla event root 下**單層**分支（兄弟＝quest node），不支援**任意深度/巢狀 SMBN 子樹**或非 vanilla event root。scope 收窄為「多層分支巢狀」，非「子樹生成」通稱。參 [[story-manager-kill-recipe]]。
- **alias 從 LeveledNpc(LVLN) 填** — 現有 fill 模式:`fromEvent`/`forced`/`uniqueActor`/`createObject`/`findMatching`（`StoryManagerEvents.cs`）。`createObject` 已能 `cro.Object.SetTo(objFk)` 帶 `Level=Easy`、且 base 可為 leveled actor → 用 `createObject:<LVLN>@<alias>` 已能把 leveled actor 生進 alias。**真缺**:沒有**一等的** LVLN-aware fill 模式，也無「createObject 之 ref 可為 LVLN」的 validation。scope:加 LVLN fill 模式，或把 createObject+LVLN 文件化/驗證化。

1. ✅ **Perk entry-point `AddActivateChoice` / `SetText` + fragment 膠水（已落地 2026-06-17）** — 新增 `PerkEffectSpec` kind `addActivateChoice`（`PerkEntryPointAddActivateChoice`：EntryType.Activate + ButtonLabel + 可選 Spell + conditions + `fragmentBody`）與 `setText`（`PerkEntryPointSetText`：Text）。**Perk fragment dispatcher**：有 fragmentBody 的 choice → `Generator.PerkFragments.cs` 生 `<perk>_Frags extends Perk`、`Fragment_<i>(akTargetRef, akActor)`；`AttachPerkFragments` 掛 `PerkAdapter` VMAD（`IndexedScriptFragment` 綁 + choice `Flags=RunImmediately|FragmentIndex`），gated on `.pex`（package 路徑，仿 quest/dialogue fragment）。`EntryPointTabCount` 補 `Activate`=2（[[perk-conditiontabcount-ctd]]）。**Mutagen shape 反射驗證**（AddActivateChoice/SetText/PerkAdapter/IndexedScriptFragment/PerkScriptFlag）；**9 測綠**，example `interactive_perk_spec.json`。⚠ PerkAdapter byte 欄（version/objectFormat、ExtraBindDataVersion、IndexedScriptFragment unknowns）+ Activate fragment 簽名待主力機 xEdit 比對真 Immersive Interactions perk（WAIT_USER）。**record-only 部分（addActivateChoice+spell、setText）離線完全可驗；fragment dispatcher 是 byte 待驗的部分。**
2. ✅ **package/marker 目標指向 quest alias（alias 間接）（已落地 2026-06-17）** — package target/location 槽支援 `alias:<name>`（ref/actor → `PackageTargetAlias`〔target〕/`LocationFallback{AliasForReference}`〔location〕）與 `aliasLoc:<name>`（location-alias → `LocationFallback{AliasForLocation}`），對 package 的 in-spec `ownerQuest` 解 alias index。共用解析 `Generator.Build.Packages.AliasRefs.cs`（`TryParseAliasRef`/`TryResolveAliasIndex`），接 `MakeLocationSlot` + `WireDeferredTargets`；validate `PkgSlotRef`（需 in-spec ownerQuest + alias 存在）。**Mutagen shape 反射驗證、8 測綠**，example `radiant_package_spec.json`。**radiant 演出鏈完整：alias 填 actor/location（#7/#8）→ package 在其上演出（#2）→ 計數 objective（#9）。** ⚠ AliasForReference/Location 選擇 + PackageTargetAlias byte 待主力機 xEdit 比對（WAIT_USER）。
3. ✅ **navmesh-tester 動態生怪 Papyrus 模板（已落地 2026-06-17）** — `QuestSpec.spawn`（`SpawnSpec{form, count, minDistance, maxDistance, snapToNavmesh}`）→ build 掛 reusable `MFDynamicSpawn` quest script（OnInit `PlaceAtMe`+`MoveTo` 玩家附近隨機偏移 + `EnableAI` toggle 吸 navmesh，EE NavmeshTester trick 的自吸附版）。`Generator.Build.StoryManager.Encounter.cs:BuildQuestSpawns`、`assets/papyrus/MFDynamicSpawn.psc`（embed CLI）、Package ShipEmbeddedPex。與 #5 locationFilter/#6 cooldownHours 共存單一 adapter → **完整動態遭遇**（地點分桶 + 防 spam + 動態生怪）。**8 測綠**，example `location_encounter_spec.json`。⚠ spawn 腳本 runtime（PlaceAtMe/EnableAI 吸附）+ .pex 編譯待主力機驗（[[programmatic-navmesh]]）。
4. 🧊 **程序化法術族生成器（高階）— 不必做（2026-06-22 決定冷凍，等非常有空再考慮）**。純便利層、不解鎖任何新 mod 類型（逐一手寫即可達同樣結果），優先 🟢 最低。無此 generator;`Generator.Build.Magic.cs` 是 1:1 spec→record。scope:在既有 builder 之上加「school × level × delivery 網格 → 對齊 MGEF+SPEL+tome」的高階層。依賴 FLST（現已確認支援）。

5. ✅ **LocType keyword 路由 + Hold 偵測（來源：IWE + EE）（已落地 2026-06-17）** — `QuestStoryEventSpec.locationFilter[]`（LocType keyword refs）→ build 在 `quest.EventConditions` 追加 OR'd `GetKeywordDataForCurrentLocation`（玩家新地點有任一 LocType 才觸發）。新增三個 condition function：`GetKeywordDataForCurrentLocation`/`LocationHasKeyword`/`LocAliasHasKeyword`（後者 hold 偵測，對 location alias 測 keyword，需 owning quest alias index）。Hold 偵測 = `findMatchingLocation` location alias + `LocAliasHasKeyword` 條件（不需專屬語法糖）。**Mutagen condition shape 反射驗證、純 CTDA 離線可驗、8 測綠**，example `location_encounter_spec.json`。
6. ✅ **WITimeout 冷卻模式（來源：EE）（已落地 2026-06-17）** — `QuestStoryEventSpec.cooldownHours`（float 遊戲小時）→ build 建 `<quest>_LastFired` float GLOB + 掛 reusable `MFEncounterCooldown` quest script（extends Quest，OnInit 比 `GetCurrentGameTime - LastFired < cooldown/24` → `Stop()` 中止重觸發；EE_WITimeout pattern）。無條件掛載（prebuilt .pex 嵌 CLI，同 scene/identity controller）。⚠ 冷卻**腳本 runtime 行為待主力機驗**（.pex 主力機編；CTDA/GLOB/掛載離線已驗）。
7. ✅ **QuestAlias `findMatchingLocation` fill 模式（LocationAlias 型）（來源：Missives）（已落地 2026-06-17）** — `QuestAliasSpec` 新增 `findMatchingLocation:<locTypeKeyword>[@<parentLocationAlias>]` fill：emit `QuestAlias.Type=Location` + `LocationAliasReference{Keyword=locType, AliasID=parent}`（建 `Generator.Build.StoryManager.cs`、驗 `Generator.Validate.StoryManager.cs`、`RadiantAliasTests`）。**Mutagen binary shape 已反射驗證**（`QuestAlias.Location=LocationAliasReference{AliasID,Keyword,RefType}`，比原推測的 CTDA 路線乾淨）。⚠ CK 語義（哪欄驅動哪個約束）待主力機 xEdit byte 比對真 Missives alias（WAIT_USER）。
8. ✅ **QuestAlias 在地點內找 ref fill 模式（來源：Missives）（已落地 2026-06-17，scope 已校正）** — **原 scope 假設用 ALNA（`FindMatchingRefNearAlias`）；反射驗證發現 ALNA `TypeEnum` 只有 `LinkedRefChild`（＝只找 editor-linked-ref 子物件，非地點內搜尋，證實既有 findMatching 註記）。** 改用 `LocationAliasReference`（其 `RefType`/LCRT 欄位對 Location 型 alias 無意義 → 證明它在 Reference 型 alias 上＝「在某 location alias 範圍內找 RefType 的 ref」）。落地 fill：`findInLocationAlias:<locationAlias>[#<refTypeLCRT>]` → `Type=Reference` + `LocationAliasReference{AliasID=locAlias, RefType=LCRT}` + conditions。Missives 的 Alias_target/Alias_chest。⚠ 同 #7，CK 語義待主力機驗。
9. ✅ **`UpdateCurrentInstanceGlobal` fragment codegen（來源：Missives）（已落地 2026-06-17）** — `StageSpec.instanceGlobals[]`（`InstanceGlobalSpec{global, randomMin/Max?, value?}`）→ `<quest>_Stages` fragment 在該 stage 生成 `<g>.SetValue(Utility.RandomInt(min,max)|值)` + `UpdateCurrentInstanceGlobal(<g>)`，把 GLOB 綁到 quest instance 讓 `<Global=X>` objective 文字顯示 per-instance 計數（同模板多開不同數量）。`Generator.QuestFragments.cs`（source + property 宣告）+ `Generator.Build.QuestStages.cs`（綁 GLOB `ScriptObjectProperty` + 該 stage QuestScriptFragment）+ `Generator.Validate.Quests.cs`（global ref/random 一致性）。**11 測綠**，example `gather_quest_spec.json`。⚠ per-instance 計數 objective 的 runtime（`SetValue`+`UpdateCurrentInstanceGlobal` 綁到當前 instance、`<Global=X>` 文字更新）待主力機驗（WAIT_USER）。**A 組 #7/#8/#9 全收 → radiant gather/bounty quest 生成鏈完整。**

## 💰 經濟 / 商販 / 服務缺口（Trade & Barter + Honed Metal 調查 2026-06-25，使用者指定；缺口已對 `src/` 驗證）

接 vendor + `settlements:` 落地後查兩個商販/服務 mod。詳見 [findings/trade-and-barter.md](../../sub_projs/mod-survey/findings/trade-and-barter.md) · [findings/honed-metal.md](../../sub_projs/mod-survey/findings/honed-metal.md)。

1. ❌ **GMST / game-setting 編輯（最乾淨的真缺口，來源 Trade & Barter）** — `src/` 證實**完全無 GMST 編輯能力**。Trade & Barter 是「一串條件化 `ModBuyPrices`/`ModSellPrices` EntryPoint perk（ModForge **已支援**，`Generator.Build.Perks.EntryPoints.cs` L31/L55）+ 一個 MCM 腳本」近乎純 perk overhaul——意味**條件化定價 perk + MCM 的經濟 tweak mod 今天就能生**，唯一缺的是調 `fBarterMin/Max`/`fSpeechcraftMin` 等之類的 GMST。建議加一個 `gameSettings:`/`gmst:` spec 區塊（純 record override，無 runtime、離線可驗、低風險），順手解鎖一大票「調平衡數值」型 mod。⚠ 待開 Trade & Barter 的 esp 用 Mutagen 確認它走 GMST vs VendorValues vs 純 perk+GLOB（agent 因 Nexus 403 無法 byte-inspect）。
2. 🟡 **`services:` macro（中價值，來源 Honed Metal；`settlements:` 的姊妹）** — 把 NPC tag 進服務 faction + 自動接條件對話開一個服務（鐵匠/附魔/訓練/代工）。scaffolding（faction + 條件服務對話 + MCM + FormList 能力清單 + 扣金幣 fragment + storage）**全在現有能力域**。**但 Honed Metal 核心是 bespoke runtime**：「開容器→腳本開原生製作選單」要 SKSE C++ DLL（ModForge 產不出，須附帶預建 asset），成本數學/perk-技能 gate 要手寫 Papyrus controller。⇒ macro 只生外殼、controller 走「附帶預寫 .pex/.dll 庫」路線。
3. 📌 **「付錢→給/改物件」交易 fragment pattern（非缺口，是可生成 macro 候選）** — 通用模板 `Player.GetGoldAmount() ≥ cost → RemoveItem(Gold) → 給/強化/附魔目標`。可重用於 vendor / 服務 / 賄賂 / 代工。乾淨、純 Papyrus fragment、離線可驗。
4. 📌 **能力清單即 FormList、由分發擴充（非缺口，是 idiom）** — Honed Metal「兩個 FormList（常見/稀有材料）+ FLM/CCOR patch 擴充」是 ModForge 已有記錄（FormList + FLM 分發）的乾淨 pattern，值得寫成 spec idiom 文件。
5. 📌 **MCM 切換 → GLOB → perk/condition 接線（待補一例）** — 「ship 一個 MCM」與「ship 一個可調機制 mod」的差別＝MCM 控件寫進 GLOB、條件/perk 讀該 GLOB。ModForge MCM + GLOB + CTDA 零件都有，缺一個把三者串起來的 worked example（Trade & Barter 是現成藍本）。
